# Flutter Android：线程模型与性能同步

源码基线：Flutter Engine ae5c3603d013477d37ae301993fc0967d4ad7ed2，于 2026-09-04 固定。本篇的“性能同步”是分析模型，不是 Flutter 的某个配置名：它指先确认工作在哪个执行者上串行、在哪个边界排队、何时受 VSync 节拍约束、何时受上下游背压或动态线程合并影响。

本篇是 Flutter Engine 专题中关于 runner 拓扑、Dart isolate 归属、合并语义和等待分类的事实源。[Android 输入到 Flutter 路由首帧](Android-输入到路由首帧.md)在此模型之上讨论一次具体交互的端到端链路。

## 范围

包含：当前固定 Engine 源码下 Android Shell 的 task runner 分配、Dart UI root isolate 的调度归属、同 runner 的直接执行、VSync 与 UI→raster 的生产消费边界，以及 Android 传统 HC Platform View 路径触发的条件性 raster/platform 动态合并。

不包含：某个应用、设备、Flutter SDK、Android 版本、trace 或卡顿结论；这些必须记录在对应项目事实源。也不把 iOS、桌面、自定义 embedder 的线程模型外推为 Android 默认。

## 先给结论

性能分析的起点不应是“Flutter 有 platform、UI、raster 三个名字，所以一定有三条线程”，而应是以下可核对的拓扑：

1. **默认 Android 路径中，platform runner 与 UI runner 是同一个 runner。**固定 Engine 的 Settings 将 merged_platform_ui_thread 默认设为 true；AndroidShellHolder 把创建时的当前 message-loop runner 设为 platform runner，并在这个设置为 true 时复用它作为 UI runner。
2. **Dart isolate 不是 task runner。**task runner 是 Engine 的 native 调度目标；普通 Flutter UI 的非 platform Dart isolate 把消息处理 runner 设为 UI runner。默认合并时，Android 平台回调和这个 UI isolate 的工作在同一条 native 执行路径上串行，而不是并发后再“同步”。
3. **raster 与 platform/UI 仍是独立的生产消费边界。**UI 侧提交 FramePipeline，Shell 将其投递到 raster runner；如果 consumer 落后，Animator 会记录 PipelineFull 并等待后续帧机会。
4. **传统 HC Platform View 路径还有另一种、条件性的合并。**本文核对的 `AndroidExternalViewEmbedder` 支持动态 raster/platform 合并，但只有实际帧含有 platform layers 时才请求合并。它与默认的 platform/UI 静态合并不是同一件事，也不能概括所有 Platform Views 模式。

所以，“线程同步”更精确地拆成：同一 runner 的串行占用、不同 runner 的投递、VSync 节拍、FramePipeline 背压，以及 Platform View 的动态 raster/platform 合并。只有先标明是哪一种，耗时才有可验证的含义。

## 四个概念，不能互换

| 概念 | 在此专题中的含义 | 不能据此推出什么 |
| --- | --- | --- |
| native thread | 操作系统实际调度的线程；AndroidShellHolder 将构造时的当前线程作为 platform thread | 不能仅凭 Flutter 概念名称推断它一定是某一条固定 OS 线程 |
| task runner | Engine 的任务调度目标。TaskRunners 保存 platform、UI、raster、IO 四个 runner 引用 | 四个字段不等于四条不同 native thread；两个字段可以指向同一个 runner |
| Dart isolate | 拥有独立 Dart 堆与事件循环的执行单元 | isolate 不是 native runner，也不自动意味着 UI 工作离开了 UI runner |
| 合并 | 两个任务队列/runner 共享执行上下文，或 raster/platform 在特定条件下临时改变执行归属 | “合并”不代表所有工作都没有等待；共享路径上的同步长任务会相互阻塞 |

## 默认拓扑：platform 与 UI 静态合并

在固定基线的 AndroidShellHolder 中，platform runner 是当前 message loop 的 runner。该实现总会创建 raster 与 IO 线程；只有 merged_platform_ui_thread 为 false 时才额外创建 UI 线程。默认 true 时，UI runner 被直接赋值为 platform runner。

    Android Shell 创建时的当前 native thread
                  │
       platform runner ─────────────┐
                                    ├── 默认：同一个 runner / 同一执行路径
       UI runner ───────────────────┘
                  │
                  ├── Android Embedding 回调、JNI、输入入口
                  ├── Dart UI root isolate 的消息、手势、业务同步代码
                  └── Scheduler、build、layout、paint

       raster runner ── 接收 FramePipeline、raster/GPU 提交
       IO runner     ── Engine IO 相关工作
       Android compositor/display ── Flutter 之外的 SurfaceFlinger/HWC/面板路径

这里的“当前 native thread”来自 Android Shell 的构造上下文。常见 Activity embedding 往往会让它对应 Android 主执行路径，但这不是应当只靠文档假定的诊断事实；遇到实际性能问题，仍应通过 trace 确认 runner 与物理线程的映射。

### Dart UI root isolate 在哪里运行

Engine 的 DartIsolate 在非 platform isolate 分支中，把其 message-handling task runner 设置为 UI runner。普通 Flutter UI root isolate 因而遵循此路径；platform isolate、service isolate、背景 helper isolate 和自定义 embedder 都不能被这一句笼统覆盖。

这也解释了默认合并的性能意义：一段长的 Java/Kotlin 平台回调、JNI 前后 native 工作、Dart 同步手势回调、路由构造或一帧 build，都可能让同一条 platform/UI 执行路径上的后续工作变晚。它是**串行占用**，不是默认 platform→UI 的跨线程交接等待。

Engine 在更新 Dart VM Service 的线程标签时，发现 platform runner 与 UI runner 相同就把 platform runner 标为 UI；源码也明确说明这不会改动底层 OS 线程名。因此，DevTools 或 VM Service 中的名称只是线索而不是物理拓扑的证明；应核对实际 queue/runner 身份和调用链。

### 同一 runner 时，输入派发怎样执行

Shell 接收指针包时先断言自己正在 platform runner，再以 UI runner 调用 RunNowAndFlushMessages。该函数在目标 runner 已是当前 runner 时直接运行任务；仅额外投递空任务，以便 message-loop observer 有机会处理平台消息处理器已排入的 Dart microtask。若目标不是当前 runner，才改为 PostTask。

因此，默认 Android 路径中的输入包不应先被归因为一次 platform→UI 跨线程排队。若 Dart 的输入回调很晚，优先检查合并 runner 上此前的 Android 或 Dart 同步工作；只有已确认非合并配置时，才把 runner 交接作为独立等待段。

## “性能同步”的五种边界

| 边界 | 真实机制 | 常见可见现象 | 首要问题 |
| --- | --- | --- | --- |
| 同 runner 串行 | platform 与 UI 默认合并；当前任务不返回，后续任务不能运行 | 输入、platform callback 或 Dart UI 回调之间有空洞 | 前一个同步任务是谁，占用了多久？ |
| 跨 runner 投递 | 非合并 UI 配置，或 UI→raster 的 PostTask | producer 已提交、consumer 晚开始 | 两端是否真是不同 runner，队列何时入队/出队？ |
| 帧节拍 | Animator 在 UI runner 投递 AwaitVSync，回调由 VSync 触发 | 业务状态已变，下一帧尚未开始 | 等的是下一次 VSync，还是 UI runner 被占用错过了节拍？ |
| 管线背压 | UI producer 取不到 FramePipeline continuation，说明 consumer 太慢 | PipelineFull、raster 侧长、重复请求后续帧 | raster 或其下游为何没有及时消费？ |
| 动态 raster/platform 合并 | 传统 HC 帧在满足条件时改变 raster/platform 的执行归属 | thread lane 变化、首个含 platform layer 的帧重试/重提 | 实际合成模式是什么，merger 是否真的激活？ |

这五类并不互斥。例如，默认合并 runner 上的长 Dart 回调可以先错过 VSync；随后的 layer tree 又可能遇到 raster 背压。分析应记录每个边界的开始和结束，而不是把总时长归给一个“线程同步”名称。

## VSync 与 UI→raster：这不是同一类等待

Scheduler 请求帧后，Animator 把 AwaitVSync 投递到 UI runner；VSync 回调到来后才开始该帧的 UI 侧处理。这个等待通常是刻意的帧节拍门槛，不是锁竞争。

UI 侧完成 layer tree 后，会将 FramePipeline 交给 Shell；Shell 再向 raster runner PostTask。Animator 若无法取得 producer continuation，会记录 PipelineFull，源码注释明确将其解释为 consumer 过慢。这一段才是 UI/raster 两端真正的生产消费关系。

对导航或点击延迟而言，应至少分开：

1. 输入或业务事件进入合并 platform/UI runner；
2. Dart 回调与路由状态改变；
3. frame request 到实际 VSync/begin frame；
4. UI build 到 layer tree 提交；
5. raster 消费与完成；
6. Android 合成与实际呈现。

第 5 步完成不等于第 6 步完成；有关 Android 显示侧的边界见 [Android 输入到 Flutter 路由首帧](Android-输入到路由首帧.md)的系统合成说明。

## 另一种合并：Platform View 的动态 raster/platform merger

不要把默认的 platform/UI 合并和 Platform View 的 raster/platform merger 混为一谈：

本节具体分析传统 HC 使用的 `AndroidExternalViewEmbedder`。HCPP 使用另一个 embedder，不能套用同一结论；其 Flutter 3.44.0 固定源码与不启用动态 merger 的证据见 [Android Platform Views 与原生渲染](../rendering/Android-Platform-Views与原生渲染.md#线程与叠加限制)。该补充使用独立版本基线，不修改本文其余线程模型的固定 revision。

| 比较项 | 默认 platform/UI 合并 | 传统 HC 动态 raster/platform 合并 |
| --- | --- | --- |
| 参与者 | platform runner 与 UI runner | rasterizer 的 raster 与 platform 执行路径 |
| 触发条件 | Settings 默认值为 true，除非启动配置或 embedder 改变 | 实际选用的 external view embedder 支持动态合并，且 Android 帧实际含 platform layers |
| 时长 | Shell 生命周期内的默认拓扑 | 以 lease 管理，能在后续帧解除 |
| 性能含义 | 平台与 Dart UI 工作彼此串行 | 某些 Platform View 帧可改由 platform 路径承担 rasterizing，转换期还可能跳过并重试该帧 |

Rasterizer 仅在存在支持该能力的 external view embedder 时创建 RasterThreadMerger。AndroidExternalViewEmbedder 虽声明支持它，却只在 FrameHasPlatformLayers 为真时请求 MergeWithLease；合并完成后，源码说明 raster task 会在 platform thread 上处理。

所以 Platform View 的存在和实际合成模式都是性能分析时必须记录的条件，不能据此推断“所有 Flutter 页面或所有原生控件都让 raster 与 platform 合并”。没有触发动态 merger 时，应按实际 Shell 配置确认 platform/UI 与 raster 的关系；纹理缓冲或 SurfaceControl 事务仍可能产生其他同步成本。

## 诊断协议：先同步拓扑，再看耗时

### 0. 建立本次 trace 的拓扑卡

每次性能结论至少记录：

- Flutter SDK、Engine revision、构建模式和 Android 版本；
- platform/UI runner 是否相同，以及它们各自映射到哪条 native thread；
- raster、IO、Android compositor 的 trace 轨道；
- 是否存在 Platform View、实际采用 VD/TLHC/HC/HCPP 哪种模式、该交互帧是否含 platform layers、动态 merger 是否激活；
- 测量端点的定义：输入、Dart 回调、frame request、begin frame、layer tree、raster finish、系统呈现。

这张卡是结论的前提，不是可选附录。同一段 trace 在默认合并与非合并/动态合并的拓扑下，含义可能不同。

### 1. 先问“谁等待谁”，不要先问“哪个 Widget 慢”

| 观察 | 优先验证的因果关系 | 不应直接下的结论 |
| --- | --- | --- |
| 输入进入早、Dart 回调晚 | 默认拓扑下查合并 runner 前方的同步占用；非合并时才查 UI runner 入队到出队 | 不能仅凭 platform/UI 两个标签断言跨线程切换 |
| Dart 状态早变、首个 build 晚 | UI runner 的事件队列、frame request 与 VSync 节拍 | 不能把所有空洞都叫做路由慢 |
| build 正常、raster 晚 | FramePipeline、raster/GPU、动态 merger 或下游图形栈 | 不能把 raster 时长直接等同于某一个 Widget 的耗时 |
| raster 已结束、画面仍未见 | Surface/BufferQueue、SurfaceFlinger、HWC/面板 | Flutter FrameTiming 不能单独证明呈现时刻 |
| 仅含 Platform View 的帧异常 | 实际合成模式、缓冲或事务同步、external view embedder、raster/platform merger 状态 | 不能仅凭存在原生控件就认定动态 merger 已激活 |

### 2. 以 flow 和端点对齐证据

Shell 的指针路径和 Animator 都写入可用于 trace 的事件；Flutter DevTools 的 Performance view 提供 UI/raster 视图。使用 profile 构建采集，并把同一次交互的应用 marker、Flutter Timeline/FrameTiming 与 Android 系统 trace 放在同一时间轴。DevTools 的 UI/raster bar 用于定位 Flutter 侧阶段，不替代 Android 实际呈现证据。

## 常见误判

- **“最新版 Flutter 已线程同步，所以不可能有输入延迟。”**默认合并减少的是 platform→UI 的跨 runner 交接；它会让平台和 UI 同步工作共享同一串行路径，长任务仍会直接推迟后续输入和 frame。
- **“UI、raster、platform 是三个固定线程。”**这是过时且过度简化的图。默认 P==U；Platform View 还可能条件性改变 raster/platform 的归属。
- **“Dart main isolate 就是一条 native UI 线程。”**二者有关联但不是同一抽象；isolate 的状态/事件循环与 Engine 的 task runner 不能互换。
- **“在 DevTools 或 VM Service 中看到名为 UI 的执行标签，就说明它与 platform 分离。”**Engine 在合并时也会使用 UI 标签；需看实际 runner/queue 身份。
- **“任何 pipeline 压力都是 GPU 坏了。”**PipelineFull 只说明 consumer 未及时消费，根因仍可能在 raster 工作、图形后端、动态线程配置或更下游的系统侧。

## 版本与适用边界

- 本文的默认值和调用关系只针对上述 Engine revision。Flutter SDK 的实际 Engine、启动参数、custom embedder、多 Engine、Platform View 组合和未来版本都可能改变运行时拓扑。
- AndroidShellHolder 的“当前线程”说明 Engine 的平台线程选择机制，不替代对实际应用线程、Looper 和 trace 轨道的确认。
- 动态 merger 是实际选用的 external view embedder 支持且帧含 platform layer 时的条件路径；本篇对应传统 HC，不外推到 TLHC、VD 或 HCPP，也不能把它当作普通 Flutter 页面上的恒定成本。
- 本篇建立的是性能归因前的模型，尚未验证任何设备或应用的实际 trace。具体阈值和优化结论必须由项目事实源持有。
