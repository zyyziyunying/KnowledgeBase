# Flutter Android：运行时性能验证链

前置阅读：[线程模型与性能同步](线程模型与性能同步.md)、[Android 输入到 Flutter 路由首帧](Android-输入到路由首帧.md)。前两篇回答固定源码基线下“理论上谁等待谁”；本篇规定怎样以真实运行时 trace 验证某次交互实际发生了什么。

协议修订日期：2026-09-10；原有来源基线为 2026-09-04，新增来源核对日期见证据包。可复查来源见[证据包](../../../evidence/flutter/engine/runtime-performance-validation/manifest.json)。

## 范围

本篇建立一条可复用的 Android Flutter 验证链：受控交互、Dart 业务 span、Flutter Engine/帧事件、Android 系统事件、Perfetto SQL 查询和可复跑产物必须能够关联到同一次操作。

不包含任何具体应用、设备、模拟器、trace、阈值或优化结论。它们属于对应项目的事实源；本仓库只保存协议、版本边界和源码入口。

## 证据与运行时验证各自回答什么

固定 revision 的 evidence 用于核对“该版本源码具有什么机制”；它不能替代以下运行时事实：实际 Flutter SDK/Engine 组合、build mode、embedder 参数、runner 到 OS thread 的映射、是否有 Platform View、渲染后端、设备刷新率，以及某一帧是否真的呈现。

一次可采信结论至少保留三类互补产物：

| 产物 | 回答的问题 | 不能替代什么 |
| --- | --- | --- |
| 固定源码/evidence | 这个版本的调用和调度机制是什么 | 不能证明目标设备真的走了该分支 |
| 运行拓扑卡 | 这次实际使用了什么 SDK、设备、构建和 runner/线程轨道 | 不能定位某次交互的时间空洞 |
| trace、配置与 SQL 结果 | 这一次操作的输入、回调、帧、raster 和系统事件何时发生 | 不应被泛化为所有设备或版本的性能结论 |

先用[线程模型与性能同步](线程模型与性能同步.md)提出待验证的等待关系，再用这条链验证或推翻它；不要先看到一个名为 UI/raster 的轨道就下结论。

## 最小闭环：端点必须分层

端点编号以[输入到首帧的最小测量点](Android-输入到路由首帧.md#最小测量点)为唯一约定：T0 系统输入分发、T1 Dart/Framework pointer 入口、T2 业务回调入口、T3 路由同步请求、T4 目标页面相关帧的 post-frame、T5 该帧的 `FrameTiming`、T6 系统呈现证据。本篇沿用这些定义，不重新编号。

`FlutterView`/Shell 指针派发是 T0→T1 的辅助观测，不能替代 T1；VSync、BUILD/LAYOUT/PAINT 和 raster slice 用于展开 T3→T5。T3 是同步区间，T5 是一组帧阶段时间戳，均不是单一时刻；计算延迟时必须写明采用区间起点、终点还是哪个 `FramePhase`。T0 还必须注明采用 down 还是 up，不能把按压时间隐含进系统延迟。

trace 名称是实现和版本相关的观测线索，不是稳定 API。例如，当前运行中可见的 `Shell::OnPlatformViewDispatchPointerDataPacket`、`Engine::DispatchPointerDataPacket` 或 `GPURasterizer::Draw`，每次都应先在目标 trace 中确认后再写入查询。

无障碍 UI 树或截图只能证明稍后看到了目标状态；它们适合验证交互确实成功，不是 T6 的时间戳。

## 采集前的拓扑卡

在按下录制前，把以下字段写入项目事实源：

- Flutter SDK、Framework revision、Engine revision、Dart 版本、构建模式和渲染后端；
- Android 版本、设备/SoC、刷新率、温控/电量状态，以及模拟器或实体设备；
- application id、入口路由、交互坐标或自动化步骤、是否含 Platform View；
- platform/UI 是否合并、raster/IO 与系统 compositor 的实际 trace 轨道；
- 本次是冷启动、冷首交互还是已预热；转场、图片、字体、shader 和数据是否已缓存；
- T0–T6 的定义、采集命令、Perfetto 配置、trace SHA-256 与执行的 SQL 文件。

没有这张卡，所谓“同一条导航”往往并不可比较。

## 给应用加入可查询的业务端点

需要在要归因的同步边界使用有起止的 span。`Timeline.timeSync` 会以 `startSync`/`finishSync` 包裹同步函数，适合给 tap 回调或 `Navigator.push` 请求命名；不要跨异步事件队列持有这个同步 span。

```dart
import 'dart:developer' as developer;

// 从 onTap/onPressed 入口直接调用；operationId 在本次采集中唯一。
void requestDetailRoute(
  BuildContext context,
  Route<void> route,
  String operationId,
) {
  developer.Timeline.timeSync('app.nav.tap/$operationId', () {
    developer.Timeline.timeSync('app.nav.push/$operationId', () {
      Navigator.of(context).push<void>(route);
    });
  });
}
```

外层 span 起点定义 T2，内层同步区间定义 T3；这里的 route 已提前构造，若要测量构造成本，应在 T3 span 内构造并记录此口径。`push` 返回的 Future 不作为首帧终点。目标页面还需在首次相关 build 中注册一次 post-frame marker，命名为 `app.nav.post_frame/<operationId>`，作为 T4 候选；不能只在 push 后注册一个全局回调就认定目标页面已参与该帧。

若查询依赖 Perfetto `slice` 表，应在目标 SDK、构建模式和采集配置下先确认 span 的名字确实出现；不要假定 instant-only marker 在所有导入器中都会以同一张表、同一种事件出现。release 模式也必须先验证所需埋点是否保留。

通过 `SchedulerBinding.addTimingsCallback` 保存 `FrameTiming` 的阶段时间戳与可用的帧标识，作为 T5。回调可能批量到达，回调执行时刻不能替代帧时间戳；它也不能单独证明 T6。

## 采集：必须启用应用级 ATrace

Flutter tool 的 `--trace-systrace` 会把 `trace-systrace=true` 传给 Android 启动路径。使用 profile（或针对发布行为的 release）构建，不能用 debug 帧时间作为性能结论。

```bash
flutter run --profile --trace-systrace -d <device-id>
```

Perfetto 的轻量模式中，`-a <application-id>` 是关键参数：它启用目标应用的 ATrace 事件；只录制 `input`、`gfx`、`view` 等系统 category，不能保证应用/Engine 的 ATrace span 会出现。

```bash
adb shell perfetto \
  -o /data/misc/perfetto-traces/<run-id>.pftrace \
  -t 30s \
  -a <application-id> \
  sched freq idle gfx view input binder_driver am wm dalvik sync

# 在录制窗口内执行一次已定义的交互；等待录制自然结束后再拉取。
adb pull /data/misc/perfetto-traces/<run-id>.pftrace <project-fact-source>/traces/
```

30 秒只是操作窗口的示例，不是性能预算。先确认 trace 服务已经开始，再触发交互；过短窗口或工具调用延迟会制造“没有输入/没有 Flutter 事件”的假阴性。长 trace 应控制 buffers、采样和类别，避免观测本身改变待测行为。

若需要 FrameTimeline，应使用包含以下 data source 的完整文本配置；上述轻量命令不保证采到它。将此段加入项目的 Perfetto 配置，同时保留 `linux.ftrace` 的系统 categories、`atrace_apps`、buffer 和 duration 设置，再运行 `adb shell perfetto --txt -c <device-config-path> -o <device-trace-path>`。

```protobuf
data_sources {
  config {
    name: "android.surfaceflinger.frametimeline"
  }
}
```

固定 Perfetto 文档要求 Android 12+，且明确标注 SurfaceView 尚不支持；这是该来源版本的边界，不能推断任一新系统仍完全相同。先核对目标 Flutter Surface/渲染路径和实际采集结果；仅有 Activity 窗口的 FrameTimeline 不能证明 Flutter Surface 的目标帧。无法覆盖时应转向目标层的 BufferQueue/fence/SurfaceFlinger 证据，并在关联不足时把 T6 标为未观测。（证据：`flutter-runtime-validation-007`。）

## 查询：固定一次操作和有限窗口

使用 Perfetto `trace_processor`，将下列查询分别保存为项目中的 SQL 文件，以 `trace_processor query -f <query.sql> <trace.pftrace>` 执行，并保留版本、参数和输出。先按唯一的 operationId 查找 T2，确认进程和线程；不直接用 application id 等同于 trace 中的 process name。

```sql
SELECT s.id, s.ts, s.dur, s.name, t.utid, p.upid, p.pid,
       p.name AS process_name, t.name AS thread_name
FROM slice AS s
JOIN thread_track AS tt ON s.track_id = tt.id
JOIN thread AS t ON tt.utid = t.utid
JOIN process AS p ON t.upid = p.upid
WHERE s.name = 'app.nav.tap/<operation-id>'
ORDER BY s.ts;
```

只有取得唯一、完整且属于目标进程的 T2 span 才继续。无结果时先排查埋点、构建模式、ATrace 配置和 trace 截断；多条时修正 operationId 或明确选定操作，不能默取第一条。以下将 `marker_id` 替换为该 `slice.id`；默认 `-1` 故意不匹配任何 marker。

```sql
WITH params AS (
  SELECT -1 AS marker_id, 200000000 AS before_ns, 2000000000 AS after_ns
), marker AS (
  SELECT s.ts, t.upid, p.before_ns, p.after_ns
  FROM params AS p
  JOIN slice AS s ON s.id = p.marker_id
  JOIN thread_track AS tt ON s.track_id = tt.id
  JOIN thread AS t ON tt.utid = t.utid
  WHERE s.dur >= 0 AND s.name GLOB 'app.nav.tap/*'
)
SELECT s.id, s.track_id, s.parent_id, s.arg_set_id,
       (s.ts - m.ts) / 1e6 AS start_from_tap_ms,
       s.dur / 1e6 AS duration_ms,
       CASE WHEN s.dur < 0 THEN 'incomplete' ELSE 'complete' END AS status,
       t.name AS thread_name, s.name
FROM marker AS m
JOIN slice AS s ON s.ts < m.ts + m.after_ns
  AND (s.dur < 0 OR s.ts + s.dur >= m.ts - m.before_ns)
LEFT JOIN thread_track AS tt ON s.track_id = tt.id
LEFT JOIN thread AS t ON tt.utid = t.utid
LEFT JOIN process_track AS pt ON s.track_id = pt.id
WHERE COALESCE(t.upid, pt.upid) = m.upid
ORDER BY s.ts, s.id;
```

前 200 ms、后 2 s 只是检索窗口，按受控操作调整并保存参数。查询保留窗口前已开始、但与窗口重叠的工作，也保留未闭合 slice 供排查；`dur < 0` 不能参与耗时统计。先查看实际名称，再筛选指针、VSync、UI 和 raster 事件。该结果只覆盖目标进程的 thread/process tracks；系统输入、调度和显示轨道需要另外查询，缺行不等于没有工作。

## 关联：从目标页面到系统呈现

时间窗口只能产生候选，不能证明因果关系。按以下顺序在项目中建立关联表，保存每一步使用的 slice id、frame/token、layer、来源字段以及关联依据：

1. 用同一 operationId 关联 T2、T3 和目标页面 T4 marker；确认 T4 位于目标页面首次参与的 UI 帧中，区分“转场首帧”和“转场完成”。若多个交互或页面重叠，先分离操作。
2. 从 T4 所在 UI 帧出发，检查实际 trace 的父子关系、flow 或已核对语义的帧标识，将它关联到 raster 和 T5。`FrameTiming` 批次顺序、时间最近、相同刷新周期都不能单独建立对应关系。Flutter 帧号与 Android token 也不能未经验证直接等值连接。
3. 沿已确认的 buffer/layer 或 token 关系寻找系统侧帧。可先查询下列候选；把时间上下限换成上一查询的同一窗口，`target_upid` 换成确认的目标进程。

```sql
WITH params AS (
  SELECT -1 AS target_upid, 0 AS start_ns, 0 AS end_ns
)
SELECT a.id, a.ts, a.dur, a.surface_frame_token, a.display_frame_token,
       a.layer_name, a.present_type, a.jank_type
FROM actual_frame_timeline_slice AS a
JOIN params AS p ON a.upid = p.target_upid
WHERE a.ts < p.end_ns
  AND (a.dur < 0 OR a.ts + a.dur >= p.start_ns)
ORDER BY a.ts, a.id;
```

4. 核对候选的 `layer_name` 确属目标 Surface，再用实际 flow 或 `display_frame_token` 找到对应的 SurfaceFlinger DisplayFrame。保留所有匹配并排除多 layer、多 display 或缺失 token 导致的歧义；应用帧的结束时间不是显示终点。只有关联成立、slice 完整且实际呈现状态支持时，才采用对应 DisplayFrame 的系统呈现端点作为 T6。丢弃帧不能算作目标画面已呈现。（证据：`flutter-runtime-validation-007`。）

不存在通用的“取 push 后第一个 raster/DisplayFrame”规则。若 T4→T5 或 T5→T6 的关联缺失，报告已确认的局部分段和缺失原因，端到端延迟记为未验证；不得将不同帧相减，或用截图时间补齐 T6。

## 时钟对齐与缺失证据

优先让应用 ATrace 和系统事件进入同一份 Perfetto trace，并使用 Trace Processor 导入后的 `ts`/`dur`（纳秒）。Perfetto 可依据 clock snapshot 将已知时钟域转换到统一 trace 时间；这不代表独立导出的 Dart/FrameTiming 日志天然与 trace 同域。（证据：`flutter-runtime-validation-006`。）

需要导入独立 `FrameTiming` 数据时：

1. 保存原始字段、单位与时钟语义；微秒转纳秒只解决单位问题。`rasterFinishWallTime` 是 wall-time，不能直接与 Perfetto `ts` 相减。
2. 在同次采集中取得对应时钟的校准点及 trace clock snapshot，并记录转换公式、校准区间和误差。以采集前后多个可关联标记检查偏移是否稳定；发生休眠或校时后重新核对，不能沿用任意固定偏移。
3. 先用转换后的时间和独立帧关联交叉核对，再计算同一帧的阶段差值。没有可验证的时钟映射时，仅报告 FrameTiming 内部 duration 和 Perfetto 内部分段，保留跨源对齐为待验证。

若所需表不存在、没有目标 Surface 帧、trace 截断或 marker 不可见，应记录具体缺失项并补采；不要把空查询结果写成“零耗时”“无掉帧”或“已呈现”。

## 归因顺序

| 观察到的空洞 | 下一步验证 | 不应直接下的结论 |
| --- | --- | --- |
| T0→T1 长 | InputDispatcher、应用主路径、Embedding/JNI，以及实际 platform/UI 拓扑 | 不能直接说 `Navigator` 慢 |
| T1→T2 长 | 手势竞技场、按压持续时间、合并 runner 的前序同步工作 | 不能只凭 `onTapDown` 作为输入抵达时间 |
| T2→T3 长或 T3 内部很长 | 回调中的同步业务、路由构造与 observer | 不能归为 raster 或显示延迟 |
| T3→T4 长 | frame request、VSync 相位和 UI build/layout/paint | 不能把正常等待下一次 VSync 叫锁竞争 |
| T4 对应 UI 工作正常、T5 中 rasterDuration 长 | raster 子 slice、资源/纹理、GPU 提交、管线背压、Platform View merger | 不能把 raster 长直接归为某个 Widget 慢 |
| T5.rasterFinish 后仍无已关联的 T6 | BufferQueue、SurfaceFlinger、HWC/FrameTimeline | `FrameTiming` 或 raster finish 不是呈现回执 |

当 T5 中 rasterDuration 很长时，继续展开该 raster slice 的嵌套事件。若耗时落在资源创建、纹理、shader、surface 包装、submit 或 fence，就把它记录为“此版本、此后端、此设备上的待验证图形路径”；再用冷/热、资源预加载和多次重复来区分稳定瓶颈与首次成本。不要从单次 emulator trace 推出 Flutter Engine 存在普遍缺陷。

## 从项目诊断走向 Engine 工作

只有同时满足下列条件，才值得把问题升级为 Engine/后端排查：

1. 同一应用、版本、设备和受控交互可重复复现；
2. T0–T6 已排除更早的输入、业务或 VSync 空洞；
3. 长 slice 已在 Engine/raster/图形交界处定位，并有嵌套事件和实际 runner 轨道支持；
4. 项目事实源固定了 Engine revision、trace、SQL、冷/热矩阵和反例；
5. 再把该 trace 名称映射回固定 revision 的 Engine 源码，而不是根据类名猜测。

这时可以针对引擎函数建立最小复现、做版本对比或在 Engine fork 中加更窄的 trace。优化前后仍用同一端点和同一矩阵验证；一次“看起来快了”的截图不是优化证据。

## 版本与验证边界

- 本篇的 `--trace-systrace`、`-a` 和 `trace_processor` 用法分别受证据包中的 Flutter tool、Perfetto CLI/ATrace 与 trace processor revision 约束；升级时先复核选项、事件名和导入表。
- Flutter 静态源码、Perfetto SQL 和 Android UI 状态各自覆盖不同层；任何一个缺失都不能补成另一个层的结论。
- 本文已核对工具与源码入口，但不保存或代表任一具体 SDK、设备、Android 分支或运行时 trace 的验证结论。实际运行结果必须由项目事实源持有。
